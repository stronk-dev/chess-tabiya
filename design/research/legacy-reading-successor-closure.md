# Legacy reading → identity-rich successor closure

**Question.** Do the richer evidence collectors replace the legacy raw structural and transition
readings along ordinary learner paths, or do both layers coexist while the web application keeps
rendering the old census?

**Verdict.** They coexist, and the old census is the only live learner path. Seventeen emitted
legacy structural reading kinds feed the position inspector and square sight; fourteen legacy
transition leaves feed the move inspector. Eight distinct richer structural projections that can
replace or derive the most voluminous old families have zero compiled consumers. All fourteen
legacy transition leaves have an identity-rich event successor, but those successors are admitted
only to `research.semantic_selection`. The returned module-registration draft would preserve the
mistake: ordinary `sight_on_request` receives all seventeen old readings, while exact mobility,
king-zone and material-role records are reserved for `full_inspector`. `[V]`

This does not mean every old predicate is wrong. Pack predicates, authoring vocabulary and compact
comparison compatibility are different jobs from learner presentation. The repair keeps useful
predicate identities while replacing ordinary output with exact, question-bound records. That
separation is what lets the foundation improve without forcing every authored pack to change each
time presentation improves.

## Method

The disposable Node-24 harness in `tools/d1726-evidence-successor-harness/` is set-equal to all 18
`STRUCTURAL_FEATURE_KINDS` and all 14 `TRANSITION_READING_PROJECTION_IDS`. It joins each legacy
family to richer compiled projections, consumer bindings, the live `DrillScreen` operation and the
returned `module-registration` table. A fixed-population census runs `structuralReading` over 611
authored + 577 imported positions and `transitionReading` over 754 + 579 committed decisions. `[V]`

The dispositions below distinguish architecture from chess judgement:

- **replace ordinary** — a richer source retains the identities needed by learner modules;
- **derive successor** — richer operands exist, but the exact learner projection does not;
- **contract pending** — a measured semantic repair must land first;
- **retain literal** — the old fact is legitimate when kept narrow;
- **retired** — no emitted reading exists and none should be resurrected.

## The returned module draft would preserve the inversion

`module-registration` correctly says legacy counts are compatibility inputs and not a second event
authority, but its literal table does the opposite for state evidence. `module.sight_on_request`
accepts all seventeen emitted `rules.structural.reading.*` rows plus square control and pawn
contacts. It omits exact/local-safe mobility, decomposed king state and material-role signature.
Those three are placed in `module.full_inspector` instead. `[V]`

That is backwards for the product contract:

- ordinary requested sight asks about one selected square or piece and needs exact identities,
  legal/local-safe destinations and a one-fact reducer;
- Advanced may expose complete topology and compatibility counts;
- a proactive nudge may use only validated, selected events with its denominator/sign rule;
- no module should receive a coarse count and its identity-rich source as competing authorities.

The draft is already returned, so this is an author correction, not an implementation rollback.

## D1727: one projection, two named-structure payloads

`structuralReading` produces both a `StructureMatch { id, name, provenanceNote }` and a separate
`StructuralObservation` whose named-structure form retains only `provenanceNote`. The generic
inspector/sight path declares evidence from the latter. Server guidance declares the same
`rules.structural.reading.named_structure@1` projection from the former. The manifest requires only
`["provenanceNote"]` and declares the payload type as a union. `[V]`

One projection identity therefore does not guarantee a pattern identity. The repair must make
`id` and `name` required sealed operands, or version a dedicated projection, and derive every
rendering from it. Parsing prose back into an id is refused.

## Five different gaps—do not call all of them “missing evidence”

| gap | measured instances | owner |
|---|---|---|
| source semantics/payload incomplete | backward pawn, opposition, outpost/denial; isolated/doubled successor; named-structure seal | D1723/D1717/D1724 and D1727/F1 |
| projection absent although operands exist | isolated/doubled; possibly a general relevant-line identity | collector RFC author |
| projection exists but no consumer binding | all eight richer structural ids | module-registration |
| consumer can be declared but no production operation emits it | semantic events; candidate/path packets | D1710 packet/path repairs |
| source and consumer exist but ordinary selection is wrong | legacy-count sight; rich-state Advanced-only | module-registration + reducers/presentation |

This vocabulary prevents a delivery bug from commissioning a duplicate detector, or a semantic
gap from being “fixed” with CSS.

## Required repair order

1. Land D1722/D1723/D1717/D1724 and seal D1727. Declare exact isolated/doubled successors from
   pawn connectivity; decide relevant-line identity separately from ray classifications.
2. Land D1710's production one-edge packet and recorded-path operation, then D1711's executable
   semantic authority. Catalogue membership or a helper call cannot activate a module.
3. Amend `module-registration` before acceptance. Ordinary sight imports exact question-bound state
   records; legacy counts stay out unless a renderer has a unique named job. Advanced may retain
   complete topology and compatibility output.
4. Make postcommit, Review, bots and longitudinal ingestion consume the same sealed exact event
   identities from packet/path operations. No Svelte detector calls or per-surface recomputation.
5. Preserve structural predicates and authored expressions until each semantic version migration
   is deliberately reviewed. Changing learner presentation alone must not churn content.
6. Generate a source→projection→consumer→operation→module receipt. A 1.0 capability closes only
   when the exact production boundary is exercised.
