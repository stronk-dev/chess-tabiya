# Competitors collapse into capabilities; love/hate evidence is the real gap

**Question:** D554–D556 — how can a fast-moving app field improve the roadmap without making every
clone, alias or launch post a new feature request?

**Verdict:** use the checked capability-first register. The first run reduces a 63-product matrix to
18 learner capabilities represented by 21 canonical products and 25 evidence rows. It covers 17 of
21 families in the 1.0 map while keeping product identity, love/hate evidence, transformation,
producer/consumer dependencies and route queryable. `[V]`
`design/research/capability-watch.json`;
`planning/platform-alignment/capability-watch/results.json`.

The instrument is complete; the market research is not. **18/25 rows (72%) have neither checked love
nor checked hate evidence.** Most of the existing corpus says what vendors offer, not why ordinary
learners keep or abandon it. The watch makes that absence explicit instead of turning a vendor page
into positive user evidence. `[V]` same summary.

## 1. Population and identity

The frozen input is the living 63-row competitor matrix plus the integrated-platform synthesis.
The representative register includes every product the owner named on 2026-08-20: Chessiverse,
Beacon, Quackmate, ChessLab at `trychesslab.com`, Qchess.net and RepCheck/RookHub, plus Chess.com,
Lichess, Chessable, an open workbench and adjacent specialist products. `[V]`
`planning/platform-alignment/capability-watch/plan.md`; register `products`.

Canonical identity is deliberate. The source matrix contains Chessiverse twice because an older
row and a richer resweep row coexist; the watch contains one product and several capability links.
“ChessLab” is bound to `trychesslab.com`; Qchess.net is not silently merged with QuChess; RepCheck
and RookHub are aliases only because the cited extension itself makes that relationship. A clone or
alias does not increase capability coverage, while a new capability id does; both controls run in
the checker. `[V]` `tools/capability-watch-harness/check.mjs`.

## 3. Coverage and honest omissions

The 17 covered map families include guidance, analysis/theory, review, drills, bots, profiles,
campaign, coach, streamer, human play, bot events, self-host/open posture, responsive workflow and
integrations. Four map families have no market representative in this seed:

- `Evidence foundation` and `Semantic move understanding` are enabling truth architecture, not
  competitor-facing features;
- `Capability watch` is this process itself;
- `Federation/discovery` is intentionally post-1.0 and waits on R17/O14.

That is not an automatic gap. The checker reports it so a later product can be attached only when
it contributes evidence. `[V]` `coveredMapFamilies`/`uncoveredMapFamilies`; `[M]` interpretation.

No row uses “not found” yet: the first pass did not run a fresh forum query per product. It uses
`not_checked`, which is the honest result. D554's hands-on/forum resweep therefore remains open and
is now cheaply targetable: prioritize the 18 missing-signal rows, not all 63 products. `[V]`

## 4. How to maintain it

1. Add or update the canonical product once.
2. Add a row only when the product supplies new evidence for a capability.
3. Record vendor capability, love signal and hate signal separately.
4. State the Tabiya transformation and the mechanism explicitly refused.
5. Bind producers, consumer, current status and research/decision/RFC route.
6. Run the checker; a clone does not create coverage and a novel capability appears unbound.

This closes D556's missing instrument. It does not close D554's requested hands-on/forum research,
authorize any feature, or replace the consumer-specific studies R3/R7/R8/R11/R15–R17. `[M]`
