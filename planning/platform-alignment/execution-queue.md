Implementation follows accepted RFC order. Completion is not a set of isolated green unit tests:

- backend primitive and frontend module bind through the manifest;
- real official-pilot content exercises the capability;
- desktop/tablet/phone and gesture-state checks run where applicable;
- provider-off/LLM-off/engine-unavailable/abstention paths are visible and useful;
- defaults and presets are tested without settings intervention;
- ledger, RFC register and exploration log close in the same commit.

F1–F4 land before large consumer work. F5/F6/F8/F9 can then integrate in parallel. F7 is the
content bridge. F10–F12 cannot fork their own evidence systems.

## Phase 9 — 1.0 release proof

The release candidate must demonstrate all included journeys in `1.0-capability-map.md` with a
fresh account and default settings, then verify:

- grounded outputs trace to their producer/source and remain true with LLM off;
- no direct-help rung appears before its allowed commitment/reveal boundary;
- no required core workflow depends on a paid/cloud service;
- import/export, delete, backup/restore and upgrade are documented and tested;
- accessibility and responsive floors pass on real interaction states;
- every deferred breadth capability is labelled honestly in docs/UI;
- H/K/C gates and limitations describe what was actually measured.

If these do not pass, the release is not “1.0 with known issues”; the failed journey returns to its
own research/decision/RFC node.
