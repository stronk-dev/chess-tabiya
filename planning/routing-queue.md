# Routing queue — explicit destinations for open ledger work

**Generated boundary, human decisions.** `make work-index` derives open/closed state from
`design/BACKLOG.md`, discovers active RFCs from `rfc/README.md`, and joins those rows to living
queue documents. It cannot derive intent: this file declares the primary destination for work
that otherwise appears only in an audit, a retired hand register, or historical prose. CI fails
when a new open row has no living destination or when a ledger id is duplicated.

This is not a claim that every row below is implementation-ready. Each lane names the next lawful
action and its gate. A reference here means “owned by this lane”, not “accepted”, “verified”, or
“scheduled ahead of the accepted RFC queue”. Active RFCs and the implementation queue continue to
set execution order.

## Ordering

1. Accepted implementation work remains ahead of draft/research lanes.
2. Collector and evidence correctness precede modules that consume them.
3. Module contracts and presets precede the final Play/Review composition pass.
4. The longitudinal store precedes player types, personalized recommendations, and opening/style reports.
5. Bot primitives may share collectors, but bot policy cannot silently become learner guidance or vice versa.
6. Campaign construction remains bound by its explicit exploration/owner gates.

`node tools/work-index.mjs --json` exposes every destination for review. The default command is a
CI assertion and intentionally prints only totals plus failures.
