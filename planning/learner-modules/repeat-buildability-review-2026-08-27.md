# Module-registration repeat independent buildability review

**Date:** 2026-08-27

**RFC:** `rfc/module-registration.md`

**Verdict:** return to author before acceptance

**Scope:** repeat buildability and production-boundary review of the D1585–D1591,
D1689–D1694 and D1854/D1855/D1858/D1859 amendment. No production or protected-design edits.

The amendment repairs the original review in substance. All 25 disposable closure arms pass:
eight over branched answer images, move-free Explorer data, reducer resealing and Match roles;
nine over the production route seam and five-mode staging controller; and eight over stable
novelty identity. The exact session/role derivations, post-commit subject ordering, generation
token and no-fake-run-revision corrections are buildable directions.

The repeat pass then traced the proposed route through the live preset store, producer execution,
F1 admission and the amended component wire. Eight blockers remain. They are not requests for
more UI polish: each is an authority or reachability gap that can produce a green registry with
wrong or permanently empty learner output.

## R1 — the server forbids the requested configuration it cannot otherwise know (D1863)

The proposal says the server derives the effective module set and forbids caller-supplied preset,
permissions and config. The requested preset and all nine primitive overrides exist only in the
browser's `tabiya.workflow.v1.*` and `tabiya.assistance.v1.*` local-storage keys. The preset loader
has no production caller. The returned `intent-presets` RFC explicitly places compilation in the
client because three of its five inputs are browser facts.

The server therefore cannot derive the learner's requested preset or explicit overrides. It can
only assume the context default, invent server state, or trust a digest whose input bytes it never
received. None makes `effectiveConfigDigest` authoritative.

**Required repair:** coordinate with the D1659–D1663 preset amendment. Send a typed requested-help
receipt as untrusted intent, including unset/explicit/migrated preference semantics and client-only
availability where relevant. The server re-derives workflow context, role, contest/campaign
ceiling and server-provider availability, clamps the request, and returns requested/effective
digests plus suppression reasons. The alternative is separately claimed server persistence; the
RFC may not pretend local storage is server-readable.

## R2 — the module path still uses the renderer the component RFC deletes (D1864)

Section 2.5 calls `renderEvidenceItems(narrowedView, MODULE_RENDERERS)` and A5 requires exactly one
renderer per projection id. `evidence-presentation` now replaces that caller-owned sentence path
with exact `projection + consumer` adapters, potentially emitting multiple sealed components/forms
for one pair. One projection may legitimately have different presentations in a nudge, Review and
Inspector.

**Required repair:** consume `presentEvidenceItems` and the closed component receipt/parser owned
by evidence-presentation. Module coverage is exact pair coverage, not one projection renderer.
Add the 186+R module pairs to D1862's set-equal component mapping (or its bounded family splits)
and prove a projection shared by two module consumers cannot swap components or sentences.

## R3 — admission starts from an evidence list no operation assembles (D1865)

`evidenceForConsumer` filters a caller-supplied `declaredEvidence` list. F1 adapter declarations
describe bindings; they do not execute collectors. The proposed `module-packets.ts` begins with
that unexplained list. The live `evidencePacket` assembler covers a small guidance subset, while
the accepted module population spans structural, tactical, transition, exchange, provider,
recorded, theory, comparison and Review operations.

A route can therefore compile every consumer and return 200 while all module populations remain
empty. Honest-empty rendering would hide the missing execution path.

**Required repair:** publish a timing × accepted-projection execution plan. It must name the
existing collector/provider operation that supplies every family, share staged/post-commit board
derivations rather than recomputing them, apply provider budgets/cancellation, and distinguish
not-requested/unavailable/no-result. A set-equal positive-reach instrument must exercise every
accepted family; empty-only fixtures cannot satisfy it.

## R4 — the no-event argument omits revealing pre/at-commit modules (D1866)

The `none` schema claim says pre-commit and at-commit modules need no delivery record because
rung-zero board arithmetic reveals nothing a learner could not see. That argument fits legal-move
dots. It does not fit a selected pattern, `threat_radar`, or a concrete
`blunder_prevention` warning. A16 names boundaries for post-commit, checkpoint and Review and none
for pre/at-commit; the at-commit candidate is transient and cannot be reconstructed from run state
after reload.

**Required repair:** reconcile this with `intent-presets`' explicit reopen condition. Either define
a narrowly scoped, auditable non-persisted disclosure receipt and amend that condition, or place
these deliveries in the durable per-learner disclosure authority. A fixture must prove the actual
pre-commit threat and at-commit warning arms, not only `rules_floor`.

## R5 — the legacy arrows consumer is neither the module nor a valid second path (D1867)

D1564 rules that the inert raw Arrows feature is replaced by a real module-backed path. The module
consumers, reducers, pair-keyed relation components and effective clamp are that path. The RFC also
orders `assistance.arrows`'s F1 disposition deleted and the consumer bound, but names no accepted
projection or adapter for it. Binding raw relation projections would create a parallel consumer
that bypasses module selection and budgets; leaving it unbound fails F1.

**Required repair:** normally retire the experimental `assistance.arrows` consumer identity while
retaining `AssistanceConfig.arrows` as the Advanced clamp over module output. If a distinct
consumer purpose survives, specify its exact non-duplicating operation and prove it cannot render
outside a module packet.

## R6 — branched capability types still have no literal declaration population (D1868)

Section 2.3 introduces the right branched capability vocabulary, but §1.1 still publishes one
singular `answerCeiling` per module. No table states the new non-empty capability set for each of
the eleven declarations. Several cannot equal the singular label: Full Inspector combines theory,
evaluation and principal-variation families; Compare combines move/fact and evaluation; Nudge and
Review combine semantic facts/threats with grades.

**Required repair:** publish the literal capability set and derived answer-content union for every
module, with set equality against its accepted projections and crossed refusals. Guided Hint keeps
its rung-specific capability contract rather than inheriting a broad module union.

## R7 — the closed request uses unvalidated semantic strings (D1869)

`selectedSquare`, `candidateUci`, `checkpointId` and `hintRung` are plain strings. A19 rejects
extra fields and foreign subject nodes, but not an invalid square, illegal or stale candidate,
checkpoint absent from the subject boundary, or rung above the effective ceiling. Browser input
normalization is not server authority.

**Required repair:** name closed parsers and authoritative membership checks for all four fields,
with typed production-boundary refusals before a collector/provider runs. Include illegal/stale
UCI, invalid square, foreign checkpoint and over-ceiling rung negatives.

## R8 — the semantic tactics foundation has no learner consumer (D1870)

The D1865 executable expansion covers all 186 declared non-hint module pairs. None accepts the
registered observed deflection, attraction, line/square clearance, interference, check
zwischenzug or overload-exploitation projections. D1067 already establishes that their
constructors are test-only and `localSemanticEvents` cannot emit multi-edge observations. The
new finding is the other half: even after a path compiler exists, F1 admission would discard all
of them from Post-commit Nudge, Review Map and Full Inspector.

**Required repair:** add the recorded-run path compiler as a dependency and publish the exact
module/timing/form acceptance set for the semantic-wave projections. Join every added pair to the
pair-keyed presentation mapping and exercise positive, no-witness and broken-boundary cases.
Engine-PV horizons remain different projections because recorded-run evidence cannot be relabelled
as hypothetical provider evidence (D1068).

## Dependency and owner boundary

Acceptance also remains mechanically premature while the RFC's own required inputs are returned:
`intent-presets` (D1659–D1663), `evidence-presentation` (D1668/D1672/D1862), the shared Explorer
source/provider execution contract, and `hint-distance`'s owner-blocked disclosure ceiling. These
are not honest-empty availability arms; they define the query input, wire and accepted population.

One product choice remains open in this RFC: whether the owner's `outpost` ruling also returns
`pawn_safe_square` to requested Sight. The author inferred yes from an identical former blocker.
Marco must confirm or narrow that one row; an implementation agent may not infer it.

## Re-review entry condition

Re-review after R1–R8 are specified against accepted or independently buildable dependencies and
the Sight owner choice is recorded. The next pass should start from four real requests—selected
square, staged move, post-commit node and Review—and prove for each:
requested intent → server clamp → collector execution → F1 pair admission → reducer → pair-keyed
component receipt → strict client parse → occupied stable seat, including positive, empty,
unavailable, stale and malicious-request arms.
