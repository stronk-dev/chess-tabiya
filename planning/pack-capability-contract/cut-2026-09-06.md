## 3. Did [[D3033]] make part of this document unnecessary? Yes — §4.1a.

§4.1a existed for exactly one reason, in its own opening sentence: *"The D560 hold makes a
same-commit 92-pack rewrite illegal today."* Because the corpus could not be restamped, the RFC had
to specify a second drill-pack reader (a sealed 0.27 mode admitting only 92 known path+digest pairs),
a distinct failure code for a changed legacy byte, an internally supplied catalogue identity so a
caller could not claim legacy membership, and **two gates that must never both pass over one tree**
(`pack-capability-software-check` before the hold lifted, `pack-capability-corpus-check` after).

[[D3033]], ruled today, dissolves the premise: *"license foundation and schema migrations before Gate
F; every authored-content and claim-binding wave stays held,"* expressly so *"the pack format can
grow so a pack can carry the evidence base."* A `requires` array projected mechanically from a
document's own content is a schema migration, not authored content. With the same-commit rewrite
legal, none of that apparatus has a job: the 0.30 schema is the only reader, and the migrating commit
rewrites all 92 documents. Criterion 3's two-sequential-gates structure and criterion 18's
legacy-reader clauses were rewritten to the one-gate shape.

**This reading is claude's, not the owner's, and is owner-vetoable.** The ruling names schema
migrations; it does not name this RFC's 92-document restamp specifically. If the owner reads the
restamp as an authored-content wave, §4.1a's compatibility reader must come back — it is recoverable
verbatim from `c37c6eb8:rfc/pack-capability-contract.md` lines 705–766, and the sealed artifact
`rfc/contracts/pack-capability-schema-transition-v1.json` was not touched.
