## What survives

The repair's architectural consolidation is sound. One catalogue, adapter dispatch by descriptor,
three lifecycle families, selector-level absence, an honest adoption transition, one canonical
byte prefix and one staged/first-parent reader are the right direction. The source-attribution
resource is now atomic, and the assistance/provider/semantic follow-ons no longer compete to own
C9/C10/C11. The existing 8/8 and 6/6 author controls reproduce.

No finding below asks for a resource-specific checker, another canonicalizer, another Git reader or
product-byte widening.

## Blocking findings

### [[D2488]] — the descriptor cannot be encoded

`SharedResourceDescriptorV1` refers to `SharedResourceProjectionV1` exactly once, as an undefined
type. The RFC never gives the projection object's keys, adapter discriminator, selector array,
version selector or adapter-option union. “Configuration is data” therefore leaves the data model
to the implementer.

### [[D2489]] — the ten-resource baseline is not literal

The initial catalogue table gives only id, lifecycle and adapter. The only literal root block names
the three absent resources. The seven existing resources have no complete descriptor image, and no
row supplies `claimMode`, `introducedBy`, `introduction`, selectors or options. The implementation
cannot produce the promised exact initial catalogue without choosing governance roots that review
never saw.

### [[D2490]] — partial state falls between resolver and projection

`ProjectedResource.state` admits only `absent | landed`, while §4 makes `partial` load-bearing for
introduction refusal and later regression. No separate selector-resolution union carries partial
into `assertSharedResourceTransition`. A thrown error is one possible implementation, a projected
state is another; the temporal contract cannot distinguish them as written.

### [[D2491]] — TypeScript closure has no traversal boundary

`typescript_contract@1` traverses local/imported types, functions, methods and constants, but does
not say what happens at Node builtins, external packages, overloads, generics, re-exports or normal
library method calls. It refuses an “unclassified repository edge” without defining the closed edge
classes. Two implementations can hash different graphs while both satisfy the prose.

### [[D2492]] — three adapters hash unspecified normal forms

The migration adapter names “normalized SQL,” the string-union adapter a “normalized union
declaration,” and versioned declarations a “complete declaration image.” None specifies an AST or
token image, comment/whitespace/alias policy, object-key canonicalization or exact included fields.
The strong canonical JSON algorithm cannot repair an undefined value before serialization.

### [[D2493]] — README ownership regresses to the rejected generator ambiguity

The implemented parent explicitly chose “check, do not generate” because `rfc/README.md` mixes
derived registers with hand-authored wave order, pins and rationale. This draft says README
“renders” from the catalogue, but defines neither a generated region nor a generic register-row
grammar nor preservation of all non-derived bytes. The implementation boundary therefore permits
both a destructive generator and another hand-maintained copy.

### [[D2494]] — the acceptance order is circular

Step 1 requires fresh review to execute all sixteen fixture families before step 2 authorizes the
engine implementation. The supplied disposable model implements canonical bytes, selector counts,
adoption and one canonical resource only; it implements none of the other six adapters, no
lifecycle and no temporal/README engine. The green author controls prove the repair's claims are
present, not that the complete design is executable.

Split the obligations: a complete disposable author model may make all sixteen pre-acceptance
families executable, or fresh review may validate a fully literal contract and leave those families
as implementation acceptance tests. The current hybrid cannot discharge D1 honestly.
